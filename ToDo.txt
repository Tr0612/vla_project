# Input Standardization Layer: Critical Missing Piece!
---

## **Architecture Design: Data Adapter Layer**

You need a **standardization pipeline** that sits **before** your VLA model:

```
Raw Dataset → Data Adapter → Standardized Format → VLA Model
```

---

## **Design Pattern: Modular Data Adapters**

### **Core Abstraction (Define Once)**

```
StandardizedObservation:
  - rgb_image: [H, W, 3] uint8, target size (e.g., 224×224)
  - language_instruction: str
  - proprioception: [D] float32, robot state
  - timestamp: float

StandardizedAction:
  - action_vector: [action_dim] float32, normalized to [-1, 1]
  - action_type: enum (EE_DELTA_POSE, JOINT_VEL, etc.)
  - gripper_state: float in [-1, 1] or binary
```

### **Per-Dataset Adapter (Implement for Each Source)**

```
BaseAdapter:
  - load_episode(episode_id) → raw data
  - process_observation(raw_obs) → StandardizedObservation
  - process_action(raw_action) → StandardizedAction
  - inverse_action(std_action) → raw_action (for deployment)
```

## **Concrete Adapter Implementations**

### **1. MetaWorld Adapter**

**Inputs:**
- Observation: Dict with 'image' (variable size) and 'state' (39-dim)
- Action: 4D (x, y, z, gripper) or 8D (x, y, z, qw, qx, qy, qz, gripper)

**Standardization Needs:**
- Resize images to 224×224
- Extract relevant proprioception (end-effector pose, gripper state)
- Normalize actions to [-1, 1] based on MetaWorld workspace bounds
- Handle quaternion vs. no-rotation tasks

**Key Transforms:**
- Image: Resize + normalize (ImageNet stats for SigLIP)
- Action: Clip to workspace bounds, then normalize
- Language: Template-based or hand-written per task

### **2. Open X-Embodiment Adapter**

**Challenges:**
- 60+ different robot embodiments

- Varying image resolutions (128×128 to 640×480)

**Standardization Strategy:**
- Image: Resize all to 224×224 (accept information loss on high-res)
- Action: Map to common 7D space (3D position + 3D rotation + gripper)
  - If source has fewer dims: Pad with zeros
  - If source has more dims: Project or truncate (document which dims are dropped)
- Proprioception: Extract common fields (EE pose, joint angles if available)
- Language: Use provided annotations or NLP templates

**Critical:** Maintain dataset ID in metadata so model can learn dataset-specific biases if needed

## **Implementation Architecture**

### **Layer 1: Dataset Registry**

```
class DatasetRegistry:
    adapters = {
        'metaworld': MetaWorldAdapter,
        'oxe_bridge': OXEBridgeAdapter,
        'oxe_rt1': OXERT1Adapter,
        'custom_moveit': MoveItAdapter,
    }
    
    def get_adapter(dataset_name, **kwargs):
        return adapters[dataset_name](**kwargs)
```

### **Layer 2: Unified DataLoader**

```
class UnifiedVLADataLoader:
    def __init__(self, dataset_configs):
        self.adapters = [
            DatasetRegistry.get_adapter(cfg.name, **cfg.params)
            for cfg in dataset_configs
        ]
        
    def __iter__(self):
        # Mix data from multiple sources
        # Return standardized batches
        for batch in mixed_sampling(self.adapters):
            yield {
                'rgb': batch.images,  # [B, 3, 224, 224]
                'text': batch.instructions,  # [B, str]
                'proprio': batch.proprioception,  # [B, D]
                'actions': batch.actions,  # [B, action_dim]
                'metadata': batch.source_info  # For debugging
            }
```

### **Layer 3: Action Space Unification**

**Critical Decision: What is your canonical action space?**

**Option A: End-Effector Delta Pose (Recommended for Manipulation)**
- 7D: [Δx, Δy, Δz, Δroll, Δpitch, Δyaw, gripper]
- All actions normalized to [-1, 1]
- Real-world deployment: Scale deltas to actual workspace limits

**Option B: End-Effector Absolute Pose**
- 7D: [x, y, z, qw, qx, qy, qz, gripper]
- Requires careful normalization (positions vs. quaternions)
- Harder to generalize across different robot bases

**Option C: Joint Space**
- N-DoF joint positions or velocities
- Robot-specific, harder to transfer across embodiments

**My Recommendation: End-Effector Delta Pose**
- Most transferable across robots
- Natural for imitation learning (small corrections)
- Matches how humans think about manipulation

## **Handling Action Space Mismatches**

### **Problem: Different Datasets Have Different Action Dimensions**

**Example:**
- MetaWorld: 4D (xyz + gripper, no rotation)
- RT-1: 7D (xyz + rpy + gripper)
- Your robot: 6D (xyz + rpy, gripper separate)

**Solutions:**

### **Solution A: Pad to Largest Dimension**
- Define max action_dim = 10 (supports most robots)
- Pad smaller actions with zeros
- Add per-dimension mask to tell model which dims are active

**Pros:** Simple, model learns to ignore padding  
**Cons:** Inefficient, model might get confused

### **Solution B: Separate Action Heads per Dataset Type**
- Group datasets by action dimension (4D, 7D, 10D)
- Use dataset-specific final layers
- Share all earlier layers (vision, text, fusion)

**Pros:** Clean separation, efficient  
**Cons:** More complex training, can't mix batches freely

### **Solution C: Action Tokenization (Advanced)**
- Discretize each action dimension into bins (e.g., 256 bins)
- Predict action as sequence of tokens
- Any number of dimensions → variable-length sequence

**Pros:** Extremely flexible, used in RT-2  
**Cons:** Complex, loses continuous control precision

**Recommendation for You: Solution A (Padding) for MVP, then Solution B if scaling up**

## **Data Mixing Strategy**

### **Challenge: Balancing Multiple Datasets**

With MetaWorld + OXE + Custom data, you need to decide sampling strategy:

### **Strategy 1: Uniform Dataset Sampling**
- Each dataset contributes equally per batch
- Batch = 25% MetaWorld + 25% OXE-Bridge + 25% OXE-RT1 + 25% Custom

**Pros:** Balanced, prevents one dataset from dominating  
**Cons:** Ignores dataset sizes, small datasets get oversampled

### **Strategy 2: Proportional to Dataset Size**
- Sample proportional to number of episodes
- Large datasets (OXE) dominate training

**Pros:** Statistically principled  
**Cons:** Small datasets (your custom) barely influence model

### **Strategy 3: Task-Based Sampling**
- Sample based on task diversity, not dataset size
- If OXE has 10 picking tasks and MetaWorld has 1, balance by task type

**Pros:** Maximizes task coverage  
**Cons:** Requires task taxonomy, complex to implement

### **Strategy 4: Curriculum Sampling (Recommended for Research)**
- Start with your custom data (most important for your use case)
- Gradually mix in MetaWorld (sim diversity)
- Finally add OXE (real-world priors)

**Pros:** Focuses on your actual deployment target  
**Cons:** Longer training schedule

## **Critical Implementation Details**

### **1. Image Preprocessing Consistency**

**All datasets must use identical preprocessing:**
```
- Resize: 224×224 (match SigLIP training)
- Normalization: ImageNet stats or SigLIP stats (be consistent!)
- Color space: RGB (not BGR from OpenCV)
- Data type: float32, range [0, 1] before normalization
```

**Common Bug:** Different datasets use different normalization → model learns dataset-specific biases instead of generalizing

### **2. Action Normalization Per Dataset**

**Each adapter needs dataset-specific bounds:**
```
MetaWorldAdapter:
  action_bounds = {
    'xyz': [(-0.3, 0.3), (-0.3, 0.3), (-0.15, 0.4)],
    'gripper': [(-1, 1)]
  }
  
OXEBridgeAdapter:
  action_bounds = {
    'xyz': [(-0.2, 0.2), (-0.2, 0.2), (0.0, 0.5)],
    'rotation': [(-π, π), (-π, π), (-π, π)],
    'gripper': [(0, 1)]
  }
```

**Normalize consistently:**
```
normalized_action = 2 * (raw_action - min) / (max - min) - 1  # → [-1, 1]
```

### **3. Language Instruction Handling**

**Challenge:** Not all datasets have rich language

**Solution: Tiered Language Strategy**
- **Tier 1:** Use provided annotations (OXE datasets often have)
- **Tier 2:** Generate from templates (MetaWorld task names → "pull the handle")
- **Tier 3:** Add variations ("grasp and pull", "execute pulling motion")

**Store language generation logic in adapters, not main model**

### **4. Coordinate Frame Consistency**

**Critical for real robot deployment:**
- MetaWorld: Robot base frame
- OXE: Varies by dataset (camera frame, world frame, robot frame)
- Your MoveIt: ROS TF frames

**Recommendation:**
- Standardize to robot base frame for all datasets
- Adapters handle frame transforms
- Document frame conventions clearly
